## Управление сессиями

Каждый пользователь получает независимую сессию с полным контекстом разговора. Управляйте сессиями с помощью команд, начинающихся с косой черты:

| Команда | Описание |
|---------|-------------|
| `/new [name]` | Начать новую сессию |
| `/list` | Показать все сессии ИИ-агента в этом проекте |
| `/switch <id>` | Переключиться на другую сессию |
| `/current` | Показать сведения о текущей сессии |
| `/history [n]` | Показать последние n сообщений (по умолчанию 10; длина каждой записи ограничена `[display].history_max_len`, по умолчанию 1000) |
| `/usage` | Показать использование квоты аккаунта/модели (если поддерживается) |
| `/provider [...]` | Управлять API-провайдерами |
| `/model [switch <alias>]` | Показать доступные модели или переключить модель по псевдониму |
| `/dir [path]` | Показать или сменить рабочий каталог ИИ-агента |
| `/allow <tool>` | Заранее разрешить инструмент (для следующей сессии) |
| `/reasoning [level]` | Просмотреть или изменить уровень усилий на рассуждение (Codex) |
| `/mode [name]` | Просмотреть или сменить режим разрешений |
| `/stop` | Остановить текущее выполнение |
| `/ps <message>` / `/btw <message>` | Отправить дополнение к выполняющейся задаче |
| `/help` | Показать доступные команды |

Во время сессии ИИ-агент может запрашивать разрешения на использование инструментов. Отвечайте **allow** / **deny** / **allow all**.

Используйте `/ps` (или `/btw`), чтобы добавить инструкции во время выполнения задачи. В сессии без выполняющейся задачи команда отклоняется. Подтверждение доставки означает, что мост отправил запрос, а не что ИИ-агент уже закончил его обработку.

При работе с Pi включите `rpc = true` для встроенной поддержки уточнений на ходу: дополнение ставится в очередь на следующий вызов модели, после вызовов инструментов в текущем ходе ассистента. Если Pi уже завершил работу, а мост ещё отправляет его ответ, дополнение запускает следующий ход. Стандартный JSON-режим Pi сохраняет прежнюю однократную отправку и не позволяет передать сообщение в уже работающий процесс.

После длительного бездействия cc-connect автоматически переходит к новой сессии:

```toml
[[projects]]
name = "demo"
reset_on_idle_mins = 30   # default when unset; set to 0 to disable
```

Следующее обычное сообщение после длительного простоя автоматически начинает новую сессию, при этом старая сессия не удаляется из `/list`.

**Почему это включено по умолчанию:** без смены сессии после простоя каждое вытеснение из пула рабочих пространств (примерно через 15 минут) приводило к тому, что следующее сообщение возобновляло предыдущий диалог через `--continue`. После многих таких циклов модель снова и снова получала устаревшую историю чата (неудачные команды, отладочный шум, оставленные побочные темы), и её внимание смещалось от исходной цели. Смена сессии после 30 минут бездействия пользователя позволяет вернуться к задаче с чистого листа, сохраняя старую сессию для `/list` и `/switch`.

Чтобы вернуть прежнее поведение с постоянным продолжением сессии, задайте `reset_on_idle_mins = 0`.

### Смена модели сохраняет историю

`/model` сохраняет текущую сессию — ИИ-агент продолжает разговор с новой моделью (без дополнительных затрат токенов). Смена модели затрагивает общий экземпляр ИИ-агента: если несколько платформ используют один проект, новая модель применяется ко всем этим платформам.

## Режимы разрешений

Все ИИ-агенты поддерживают режимы разрешений, которые можно переключать во время работы через `/mode`.

### Режимы Claude Code

| Режим | Значение в конфигурации | Поведение |
|------|-------------|----------|
| По умолчанию | `default` | Каждый вызов инструмента требует подтверждения |
| Разрешение правок | `acceptEdits` / `edit` | Правки файлов разрешаются автоматически |
| Автоматический | `auto` | Claude решает, когда запрашивать разрешение |
| Планирование | `plan` | Claude только планирует, ничего не выполняя |
| YOLO | `bypassPermissions` / `yolo` | Все инструменты разрешаются автоматически |

### Режимы Codex

| Режим | Значение в конфигурации | Поведение |
|------|-------------|----------|
| Предложения | `suggest` | Без подтверждения выполняются только доверенные команды |
| Автоматическое редактирование | `auto-edit` | Модель решает, когда запрашивать подтверждение |
| Полностью автоматический | `full-auto` | Автоматическое разрешение с использованием песочницы |
| YOLO | `yolo` | Обход всех подтверждений и песочницы |

### Поиск Codex CLI в macOS

Адаптер Codex выбирает исполняемый файл в следующем порядке:

1. Параметр проекта `cmd` (включая устаревшие псевдонимы `cli_path` / `command`).
2. `CODEX_CLI_PATH` из окружения, в котором запускается cc-connect, если команда не задана в конфигурации.
3. Исполняемый файл `codex` в `PATH` этого процесса.
4. В macOS — `/Applications/ChatGPT.app`, затем `/Applications/Codex.app`. В каждом приложении сначала проверяется актуальное расположение `Contents/Resources/codex-cli/CodexCLI.app/Contents/MacOS/codex`, затем устаревшее `Contents/Resources/codex`.

Поиск в настольных приложениях выполняется, если команда отсутствует в PATH или символическая ссылка в PATH не работает. Явно заданная команда или `CODEX_CLI_PATH` должны указывать на исполняемый файл; некорректное переопределение приводит к ошибке. Поиск повторяется перед каждым запуском процесса CLI, чтобы учитывать изменения расположения встроенных файлов после обновления приложения. В Linux и Windows по-прежнему используется команда из конфигурации или PATH.

Этот выбор применяется к `exec` и `app_server`, чтению конфигурации во время работы, запросам навыков и `/doctor`. Для путей с пробелами или дополнительных аргументов CLI используйте форму массива:

```toml
[projects.agent.options]
cmd = ["/path with spaces/codex", "--profile", "work"]
```

Так встроенный CLI запускается через существующий адаптер Codex. Для инструментов, доступных только в настольном приложении, и блокировки записи в общие диалоги действуют отдельные требования; см. [обсуждение настольного бэкенда #651](https://github.com/chenhg5/cc-connect/issues/651) и [конфликт записи в диалог #1909](https://github.com/chenhg5/cc-connect/issues/1909).

### Режимы Cursor Agent

| Режим | Значение в конфигурации | Поведение |
|------|-------------|----------|
| По умолчанию | `default` | Доверять рабочему пространству, запрашивать разрешение перед использованием инструментов |
| Принудительный (YOLO) | `force` / `yolo` | Автоматически разрешать всё |
| Планирование | `plan` | Анализ только для чтения |
| Вопросы и ответы | `ask` | Формат вопросов и ответов, только чтение |

### Режимы Gemini CLI

| Режим | Значение в конфигурации | Поведение |
|------|-------------|----------|
| По умолчанию | `default` | Запрашивать подтверждение |
| Автоматическое редактирование | `auto_edit` / `edit` | Автоматически разрешать правки |
| YOLO | `yolo` | Автоматически разрешать всё |
| Планирование | `plan` | Режим планирования только для чтения |

### Qoder CLI / OpenCode / iFlow CLI

| Режим | Значение в конфигурации | Поведение |
|------|-------------|----------|
| По умолчанию | `default` | Стандартные разрешения |
| YOLO | `yolo` | Пропускать все проверки |

### Конфигурация

```toml
[projects.agent.options]
mode = "default"
# allowed_tools = ["Read", "Grep", "Glob"]
```

Переключение во время работы:
```
/mode          # show current and available modes
/mode yolo     # switch to YOLO mode
/mode default  # switch back
```

## Управление API-провайдерами

Переключайтесь между API-провайдерами во время работы без перезапуска.

### Настройка провайдеров

```toml
[projects.agent.options]
work_dir = "/path/to/project"
provider = "anthropic"   # active provider

[[projects.agent.providers]]
name = "anthropic"
api_key = "sk-ant-xxx"

[[projects.agent.providers]]
name = "relay"
api_key = "sk-xxx"
base_url = "https://api.relay-service.com"
model = "claude-sonnet-4-20250514"

[[projects.agent.providers.models]]
model = "claude-sonnet-4-20250514"
alias = "sonnet"

[[projects.agent.providers.models]]
model = "claude-opus-4-20250514"
alias = "opus"

[[projects.agent.providers.models]]
model = "claude-haiku-3-5-20241022"
alias = "haiku"

# MiniMax — OpenAI-compatible agent provider, 1M context
[[projects.agent.providers]]
name = "minimax"
api_key = "your-minimax-api-key"
# Use https://api.minimaxi.com/v1 for China-region accounts.
base_url = "https://api.minimax.io/v1"
model = "MiniMax-M2.7"

# For Bedrock, Vertex, etc.
[[projects.agent.providers]]
name = "bedrock"
env = { CLAUDE_CODE_USE_BEDROCK = "1", AWS_PROFILE = "bedrock" }
```

### Команды CLI

```bash
cc-connect provider add --project my-backend --name relay --api-key sk-xxx --base-url https://api.relay.com
cc-connect provider list --project my-backend
cc-connect provider remove --project my-backend --name relay
cc-connect provider import --project my-backend  # from cc-switch
```

### Команды чата

```
/provider                   Show current provider
/provider list              List all providers
/provider add <name> <key> [url] [model]
/provider remove <name>
/provider switch <name>
/provider <name>            Shortcut for switch
```

### Соответствие переменных окружения

| ИИ-агент | api_key → | base_url → |
|-------|-----------|------------|
| Claude Code | `ANTHROPIC_API_KEY` | `ANTHROPIC_BASE_URL` |
| Codex | `OPENAI_API_KEY` | `OPENAI_BASE_URL` |
| Gemini CLI | `GEMINI_API_KEY` | используйте словарь `env` |
| OpenCode | `ANTHROPIC_API_KEY` | используйте словарь `env` |
| iFlow CLI | `IFLOW_API_KEY` | `IFLOW_BASE_URL` |

## Выбор модели

Заранее задайте список доступных для выбора моделей каждого провайдера с помощью `[[providers.models]]`. Каждая запись содержит идентификатор `model` и необязательный `alias` — короткое имя, отображаемое в `/model`.

### Настройка моделей

```toml
[[projects.agent.providers]]
name = "openai"
api_key = "sk-xxx"

[[projects.agent.providers.models]]
model = "gpt-5.3-codex"
alias = "codex"

[[projects.agent.providers.models]]
model = "gpt-5.4"
alias = "gpt"

[[projects.agent.providers.models]]
model = "gpt-5.3-codex-spark"
alias = "spark"
```

### Команды чата

```
/model              List available models (format: alias - model)
/model switch <alias>      Switch to the model matching the alias
/model switch <name>       Switch to the model by its full name
/model <alias>             Legacy syntax, still supported
```

Если `models` задан, `/model` показывает именно этот список, не обращаясь к API. Если параметр отсутствует, модели загружаются через API провайдера либо используется встроенный резервный список.

## Смена рабочего каталога (`/dir`, `/cd`)

Меняйте каталог, в котором начнётся следующая сессия ИИ-агента, прямо из чата.

### Команды чата

```
/dir                    Show current work directory and recent history
/dir <path>             Switch to a path (relative or absolute)
/dir <number>           Switch to a directory from history
/dir -                  Switch back to previous directory
/dir help               Show command usage
/cd <path>              Backward-compatible alias of /dir <path>
```

### Особенности работы

- `/dir` — привилегированная команда. Для её использования необходимо задать `admin_from` в секции `[[projects]]` файла `config.toml`.
- Не размещайте `admin_from` в `[projects.platforms.options]`: там параметр будет проигнорирован.
- Используйте `/whoami` или `/status`, чтобы узнать свой текущий `User ID`, затем укажите этот идентификатор в `admin_from`.
- Если вы единственный пользователь бота, можно задать `admin_from = "*"`, но это предоставляет доступ к привилегированным командам всем допущенным пользователям.
- После изменения `config.toml` перезапустите `cc-connect`.
- Смена каталога применяется к следующей сессии в текущем проекте.
- Относительные пути разрешаются от текущего рабочего каталога ИИ-агента.
- История каталогов хранится отдельно для каждого проекта; переключаться можно по номеру записи.
- `/cd` сохранена для совместимости, но основной командой является `/dir`.

Пример конфигурации:

```toml
[[projects]]
name = "my-project"
admin_from = "ou_xxx"
```

Примеры:

```text
/dir ../another-repo
/dir 2
/dir -
```

## Запуск ИИ-агентов от другого пользователя Unix (`run_as_user`)

> **Поддерживаемые платформы**: Linux и macOS. В Windows не поддерживается.
> **Поддерживаемые ИИ-агенты**: на данный момент Claude Code. Остальные ИИ-агенты запускаются
> от пользователя управляющего процесса; состояние их перевода см. в задаче, отслеживающей эту работу.

### Назначение

По умолчанию каждая сессия ИИ-агента, которую запускает cc-connect, работает от того же пользователя Unix, что и сам `cc-connect`. Если ИИ-агент действует некорректно — читает секрет, перезаписывает соседний репозиторий, повреждает `~/.ssh/`, — ему доступна вся область файловой системы, доступная пользователю управляющего процесса.

`run_as_user` задаёт целевого пользователя Unix для отдельного проекта. Если параметр указан, cc-connect запускает команду ИИ-агента этого проекта через

```
sudo -n -iu <target-user> -- claude ...
```

Целевой пользователь — настоящая непривилегированная учётная запись Unix, которую вы создаёте. ИИ-агент работает с uid/gid этой учётной записи, с **собственным** домашним каталогом, профилем командной оболочки, PATH и учётными данными для инструментов. Изоляцию файловой системы обеспечивает ядро, а не обработчики или списки разрешений.

### Гарантии и ограничения безопасности

**Это обеспечивает изоляцию на уровне пользователя ОС от любых файлов и процессов, к которым целевой пользователь не имеет доступа.** ИИ-агент больше не может читать или повреждать `~/.ssh/` пользователя управляющего процесса, `~/.pgpass` пользователя другого проекта или репозиторий, права UNIX которого не предоставляют доступ целевому пользователю.

**Это не изолирует проекты друг от друга автоматически**, если они используют одно и то же значение `run_as_user`. Для изоляции проектов создавайте отдельного пользователя Unix для каждого проекта.

**Это не песочница на основе пространств имён Linux, seccomp или контейнерной изоляции.** Механизм лишь ограничивает доступ к файловой системе по uid.

### Настройка

#### 1. Создайте целевого пользователя и установите его инструменты

Целевому пользователю нужны собственные копии всего, с чем работает ИИ-агент: `sudo -i` загружает окружение входа *целевого* пользователя, а не пользователя управляющего процесса.

```bash
sudo useradd -m -s /bin/bash partseeker-coder
sudo -iu partseeker-coder

# Install the agent CLI under the target user's PATH
#   (for Claude Code, follow the normal install instructions)

# Set up the target user's ~/.claude/
mkdir -p ~/.claude
# Copy or re-create:
#   ~/.claude/settings.json     (MCP servers, hooks, model settings)
#   ~/.claude.json              (Claude Code auth)
#   ~/.claude/plugins/          (claude-mem and any other plugin state)

exit
```

#### 2. Разрешите пользователю управляющего процесса sudo без пароля от имени целевого пользователя

Добавьте правило sudoers с ограниченной областью действия. **Не** предоставляйте пользователю управляющего процесса `NOPASSWD: ALL` без ограничения целевой учётной записи: это даёт ему права root, которые здесь не нужны и опасны.

```
# /etc/sudoers.d/cc-connect (install with `sudo visudo -f ...`)
partseeker-orchestrator ALL=(partseeker-coder) NOPASSWD: ALL
```

Замените имена пользователей на свои. Правило означает: *«Пользователь управляющего процесса может выполнять любую команду от имени именно этого целевого пользователя без пароля».*

#### 3. Убедитесь, что целевой пользователь не может выполнять sudo

Смысл перехода к целевому пользователю с меньшими правами в том, чтобы он не мог сразу повысить их обратно. Проверьте:

```bash
sudo -n -iu partseeker-coder -- sudo -n true
# must FAIL with "a password is required" or similar
```

Если команда завершается успешно, cc-connect откажется запускаться. Сначала удалите все разрешения sudo с `NOPASSWD` для целевого пользователя.

#### 4. Предоставьте целевому пользователю доступ к `work_dir` проекта

Целевому пользователю необходимы права на чтение И запись в `work_dir` проекта. Если каталог принадлежит пользователю управляющего процесса, передайте его целевому пользователю через `chown`, назначьте каталог группе, в которую входит целевой пользователь, или примените POSIX ACL:

```bash
sudo setfacl -R -m u:partseeker-coder:rwX /home/leigh/workspace/sandboxed-repo
sudo setfacl -R -dm u:partseeker-coder:rwX /home/leigh/workspace/sandboxed-repo
```

cc-connect отказывается запускаться, если целевой пользователь не может читать и записывать в корень `work_dir`, и выдаёт предупреждения (не препятствующие запуску) для вложенных путей, которые выглядят недоступными.

#### 5. Проверьте настройку перед запуском cc-connect

```bash
cc-connect doctor user-isolation
```

Команда выполняет полную предварительную проверку (три проверки допуска к запуску из [#496](https://github.com/chenhg5/cc-connect/issues/496)) и **проверку изоляции**: запускает фиксированный shell-скрипт от имени целевого пользователя и сообщает, что ему доступно для чтения, к чему доступ запрещён и есть ли утечки между пользователями. Результат выводится в stdout, а JSON-отчёт сохраняется в `~/.cc-connect/audits/<timestamp>-<project>.json`.

Код завершения 0 = проблем нет. Код завершения 1 = есть хотя бы одна критическая проблема.

Сам проверочный скрипт можно просмотреть командой:

```bash
cc-connect doctor user-isolation --print-script
```

### Передача окружения: что перенести в домашний каталог целевого пользователя

Этот раздел пригодится, когда отладка затянется до двух часов ночи. При переводе проекта на `run_as_user` окружение пользователя управляющего процесса **не** передаётся через sudo — в этом и заключается смысл механизма. Всё необходимое ИИ-агенту должно находиться в домашнем каталоге целевого пользователя.

Контрольный список переноса:

- [ ] **Конфигурация ИИ-агента** — `~/.claude/settings.json` (MCP-серверы, обработчики,
      настройки модели), `~/.claude.json` (аутентификация). Скопируйте файлы у пользователя
      управляющего процесса или создайте заново.
- [ ] **Состояние плагинов** — `~/.claude/plugins/` — claude-mem и любые другие
      плагины Claude Code.
- [ ] **Исполняемые файлы MCP-серверов** — должны быть в `PATH` целевого пользователя,
      а не только пользователя управляющего процесса. Установите их от имени целевого пользователя
      или укажите полные пути в `settings.json`.
- [ ] **Postgres TLS** — `PGSSLROOTCERT`, `PGSSLCERT`, `PGSSLKEY` следует задать
      в блоке `env` файла `~/.claude/settings.json` целевого пользователя.
      Указанные в них файлы сертификатов должны быть доступны ему для чтения.
- [ ] **Учётные данные Claude OAuth** — если вы входите через `claude.ai`
      (OAuth), токен хранится в `~/.claude/.credentials.json`. Срок действия токенов
      доступа OAuth истекает через несколько часов; их автоматически обновляет
      работающая сессия Claude CLI. Токен целевого пользователя **не** обновляется,
      если у него нет активной сессии, что часто бывает между запусками
      ИИ-агента из cc-connect. Рекомендуемое решение — заменить файл учётных данных
      целевого пользователя символической ссылкой на файл пользователя управляющего процесса,
      чтобы обе учётные записи использовали один постоянно обновляемый токен:

      ```bash
      # Grant target user read access via ACL (keeps 600 for everyone else)
      setfacl -m u:<target-user>:rx ~/.claude/
      setfacl -m u:<target-user>:r  ~/.claude/.credentials.json

      # Replace the target user's credentials with a symlink
      sudo -iu <target-user> bash -c \
        'rm -f ~/.claude/.credentials.json && \
         ln -s /home/<supervisor>/.claude/.credentials.json \
               ~/.claude/.credentials.json'
      ```

      **Если вместо OAuth используется API-ключ** (`ANTHROPIC_API_KEY`),
      этой проблемы нет: задайте ключ в блоке `env` файла
      `~/.claude/settings.json` целевого пользователя, и срок его действия не истечёт.
- [ ] **Файлы учётных данных** — `~/.pgpass`, `~/.gitconfig`, `~/.netrc`,
      `~/.aws/`, `~/.config/gh/`, `~/.kube/` — те, которыми ИИ-агент
      действительно пользуется. Для каждого нужна отдельная копия или общая копия,
      доступная группе для чтения.
- [ ] **SSH-ключи** — `~/.ssh/id_ed25519` и т. п., если ИИ-агент выполняет `git
      push` через SSH. Аналогично: скопируйте их или предоставьте общий доступ через группу.
- [ ] **Ключевые материалы в** `~/keys/` — для нестандартных каталогов, которые использует
      пользователь управляющего процесса, нужны аналоги в домашнем каталоге целевого пользователя
      либо общая копия, доступная группе для чтения.
- [ ] **Инструментарий языков программирования** — если ИИ-агент использует `asdf`, `mise`, `nvm`,
      `rustup` и т. п., они находятся в `~`. Целевому пользователю нужна
      собственная установка либо общесистемная, доступная обоим пользователям.
- [ ] **Профиль командной оболочки** — `~/.profile` / `~/.bashrc` целевого пользователя
      должен задавать `PATH` и выполнять инициализацию всех инструментов, от которых зависит ИИ-агент.
      Проверьте это через `sudo -iu partseeker-coder` до подключения cc-connect.

После переноса снова выполните `cc-connect doctor user-isolation`. Раздел `target home` показывает, какие ожидаемые пути существуют, а какие отсутствуют. Отсутствие не обязательно означает ошибку, но этот список поможет всё проверить.

### Отключение

Удалите `run_as_user` из записи проекта или задайте `""`. При следующем перезапуске вернётся прежнее поведение — запуск от пользователя управляющего процесса.

### Возможные сбои и сообщения об ошибках

- **"passwordless sudo to user X is not configured"** — пропущен шаг 2 настройки
  или правило sudoers относится не к тому пользователю управляющего процесса. Исправьте
  правило, проверьте синтаксис командой `visudo -c`, затем перезапустите cc-connect.
- **"target user X can run passwordless sudo"** — проверка на шаге 3 не пройдена.
  Сообщение об ошибке содержит вывод `sudo -l` от имени целевого пользователя;
  найдите правило, предоставляющее эти права, и удалите его.
- **"target user X cannot read AND write work_dir Y"** — проверка на шаге 4 не пройдена.
  Смените владельца каталога через `chown` или добавьте ACL, как показано выше.
- **"CROSS_LEAKED"** или **"SUPERVISOR_LEAKED"** в отчёте аудита —
  целевой пользователь может читать секреты другого пользователя. Ограничьте права
  проблемного файла (обычно `chmod 600 file; chown user:user file`)
  и повторите аудит.
- **"descendant scan timed out"** — некритическая ошибка. Каталог `work_dir` настолько велик,
  что проверка прав вложенных путей превысила отведённое время. Для полного обхода
  выполните `cc-connect doctor user-isolation` вручную
  или сузьте область `work_dir` проекта.

## Настройка Feishu через CLI

Используйте CLI, чтобы создать или привязать учётные данные бота Feishu/Lark и записать их в `config.toml`.

```bash
# Recommended: unified entry
cc-connect feishu setup --project my-project
cc-connect feishu setup --project my-project --app cli_xxx:sec_xxx

# Force modes (usually unnecessary)
cc-connect feishu new --project my-project
cc-connect feishu bind --project my-project --app cli_xxx:sec_xxx
```

Различия:
- `setup`: единая точка входа. Без учётных данных работает как `new`; с `--app` — как `bind`.
- `new`: принудительно запускает подключение через QR-код; не принимает `--app`.
- `bind`: принудительно запускает привязку учётных данных; требует их указания.

Поведение:
- По умолчанию `setup` использует подключение через QR-код, а при указании `--app` — режим привязки.
- Если проект, указанный в `--project`, не существует, он создаётся автоматически.
- Если проект существует, но в нём нет платформы `feishu/lark`, она добавляется автоматически.
- Команда записывает учётные данные (`app_id`, `app_secret`); при подключении через QR-код Feishu обычно заранее настраивает разрешения и подписки на события.
- Тем не менее проверьте статус публикации приложения и область его доступности в Feishu Open Platform.
- Конфигурация платформы, используемая во время работы, также поддерживает необязательное переопределение `domain` для адресов API Feishu/Lark; оно не меняет URL настройки и первоначального подключения.

## Настройка Weixin (личный аккаунт) через CLI

Личные чаты Weixin используют **ilink bot HTTP API** (длительный опрос сервера, long polling, + `sendMessage`; то же семейство API, что у OpenClaw `openclaw-weixin`). Через CLI можно отсканировать QR-код или привязать существующий Bearer-токен и записать `config.toml`.

**Полное пошаговое руководство (на китайском): [docs/weixin.md](./weixin.md).**

```bash
cc-connect weixin setup --project my-project
cc-connect weixin bind --project my-project --token '<token>'
cc-connect weixin new --project my-project
```

Примечания:
- `setup` без `--token` запускает вход по QR-коду; с `--token` работает как bind.
- Если проект и/или блок платформы `weixin` отсутствуют, они создаются автоматически.
- После входа отправьте одно сообщение из WeChat, чтобы `context_token` сохранился в кеше.
- Список флагов (`--api-url`, `--cdn-url`, `--route-tag` и др.) см. в `cc-connect weixin help`.

## Обработчики PermissionRequest в Claude Code

Если в вашем `settings.json` для Claude Code настроены [обработчики PermissionRequest](https://docs.anthropic.com/en/docs/claude-code/hooks), cc-connect учитывает их: подходящие обработчики могут автоматически разрешать или отклонять запросы инструментов до их отправки на платформу обмена сообщениями.

### Почему обработчики запускаются дважды

cc-connect запускает Claude Code с `--permission-prompt-tool stdio`, поэтому вывод обработчиков, выполненных самим Claude Code, отбрасывается (stdout занят протоколом). Чтобы обработчики действительно влияли на результат, cc-connect читает их определения из `settings.json` и **повторно запускает их самостоятельно**.

Это означает, что команда обработчика выполняется **дважды** на каждый запрос разрешения:

1. Один раз — Claude Code (результат отбрасывается)
2. Один раз — cc-connect (результат используется)

### Как избежать двойных затрат в обработчиках на основе LLM

Если обработчик основан на правилах (например, «запретить `rm -rf`»), двойное выполнение безвредно. Но если он обращается к большой языковой модели, LLM (как [ccgate](https://github.com/tak848/ccgate)), первый запуск расходует токены впустую. Добавьте следующую проверку в начало обработчика:

```bash
#!/bin/bash
if [ -n "$CC_CONNECT_PERMISSION_HOOK_SKIP" ]; then
  exit 0  # cc-connect will re-run us without this flag
fi
# ... your actual hook logic ...
```

cc-connect задаёт `CC_CONNECT_PERMISSION_HOOK_SKIP=1` в окружении дочернего процесса Claude Code. Если обработчик видит эту переменную, он выполняется внутри Claude Code, и его результат будет отброшен — затратную работу следует пропустить. При самостоятельном запуске обработчика cc-connect удаляет эту переменную, поэтому второе выполнение проходит как обычно.

## Голосовые ответы (преобразование текста в речь)

Преобразуйте ответы ИИ в голосовые сообщения с помощью синтеза речи.

**Поддерживаются:** платформы, в которых реализована отправка аудио, например Feishu/Lark, DingTalk, Telegram, Max и Weixin.

### Настройка

```toml
[tts]
enabled = true
provider = "minimax"     # qwen | openai | minimax | mimo | espeak | pico | edge
voice_id = "Chinese (Mandarin)_Crisp_Girl"
speed = 0.98             # provider-specific range; MiniMax commonly accepts 0.5-2.0
tts_mode = "voice_only"  # "voice_only" | "always"
max_text_len = 0         # 0 = no limit

[tts.minimax]
api_key = ""             # optional: falls back to data_dir/config/minimax.json
base_url = ""            # optional: default https://api.minimaxi.com
model = "speech-2.8-hd"

[tts.agents.assistant]
voice_id = "Chinese (Mandarin)_Crisp_Girl"
speed = 0.98

[tts.agents.reviewer]
voice_id = "Chinese (Mandarin)_Gentle_Senior"
speed = 0.96
```

### Режимы TTS

| Режим | Поведение |
|------|----------|
| `voice_only` | Отвечать голосом только на голосовые сообщения пользователя |
| `always` | Всегда отправлять голосовой ответ |

Переключение: `/tts always` или `/tts voice_only`

## Отправка изображений, файлов и голоса в чат

Когда ИИ-агент создаёт локальное изображение, PDF, отчёт, архив или другой файл и должен передать его прямо в текущий чат, используйте режим вложений команды `cc-connect send`. Если пользователь явно просит голосовое сообщение, ИИ-агент также может отправить синтезированную речь через тот же CLI.

**Платформы, поддерживаемые на данный момент:**
- Feishu
- Telegram

### Когда сначала нужно выполнить setup

Если текущий ИИ-агент не поддерживает встроенное внедрение системного промпта, после обновления один раз выполните в чате:

```text
/bind setup
```

или:

```text
/cron setup
```

Эти две команды записывают одинаковые инструкции cc-connect. Достаточно любой из них. После этого ИИ-агент знает, что:
- обычные текстовые ответы нужно возвращать привычным способом
- созданные вложения нужно отправлять через `cc-connect send --image/--file`
- запрошенные голосовые сообщения нужно отправлять через `cc-connect send --tts`

Если вы уже выполняли setup, выполните его снова после обновления, чтобы получить актуальную версию инструкций.

### Переключатель в конфигурации

Чтобы запретить ИИ-агенту отправлять вложения в чат, добавьте в `config.toml`:

```toml
attachment_send = "off"
```

По умолчанию используется `on`. Этот переключатель независим от `/mode` ИИ-агента и влияет только на `cc-connect send --image/--file`. Отправка синтезированной речи использует конфигурацию провайдера `[tts]` и определяется доступностью TTS.

### Примеры CLI

```bash
cc-connect send --image /absolute/path/to/chart.png
cc-connect send --file /absolute/path/to/report.pdf
cc-connect send --file /absolute/path/to/report.pdf --image /absolute/path/to/chart.png
cc-connect send --tts "Hello from cc-connect"
```

Примечания:
- `--image` предназначен для вложений-изображений.
- `--file` предназначен для любых файловых вложений.
- `--tts` синтезирует речь из текста и отправляет полученное аудио через активного TTS-провайдера.
- `--message` необязателен: он отправляет текстовое пояснение перед вложениями.
- `--image` и `--file` можно указывать несколько раз.
- Рекомендуется использовать абсолютные пути, чтобы команда не зависела от текущего рабочего каталога ИИ-агента.
- При `attachment_send = "off"` отправка изображений и файлов блокируется, но обычные текстовые ответы продолжают работать.
- Размер каждого вложения по умолчанию ограничен **50 MiB**. Настройте ограничение через `max_attachment_size_mb` (в MiB) в config.toml или переопределите его переменной окружения `CC_MAX_ATTACHMENT_SIZE_MB` (в тех же единицах MiB; если задана, имеет приоритет), например: `CC_MAX_ATTACHMENT_SIZE_MB=100 cc-connect send --file big.bin`.

### Типичные сценарии

1. ИИ-агент создаёт скриншот или диаграмму и должен отправить их прямо пользователю.
2. ИИ-агент создаёт PDF, экспорт в Markdown, архив журналов или файл патча, который нужно передать как вложение.
3. ИИ-агент хочет отправить короткое сообщение о состоянии вместе с одним или несколькими созданными файлами.
4. Пользователь просит ИИ-агента «отправить это голосом», не вводя команду с косой чертой.

### Важные замечания

- Эта команда предназначена для отправки созданных вложений и голосовых сообщений, а не для обычных текстовых ответов.
- Файлы должны существовать на локальной машине, где работает ИИ-агент.
- Необходима активная сессия; иначе команда завершается ошибкой, поскольку у cc-connect нет контекста чата для доставки.
- При доставке целевая платформа также применяет собственные ограничения на размер и тип файлов. Фактический предел размера вложения равен меньшему из ограничения платформы и `max_attachment_size_mb` (файл, прошедший проверку cc-connect, всё ещё может быть отклонён платформой).

## Задачи по расписанию (Cron)

Создавайте задачи по расписанию для автоматического периодического запуска.

### Команды чата

```
/cron                                          List all jobs
/cron add <min> <hour> <day> <mon> <wk> <prompt>   Create job
/cron del <id>                                 Delete job
/cron enable <id>                              Enable job
/cron disable <id>                             Disable job
```

Пример:
```
/cron add 0 6 * * * Summarize GitHub trending repos
```

### Команды CLI

```bash
cc-connect cron add --cron "0 6 * * *" --prompt "Summarize GitHub trending" --desc "Daily Trending"
cc-connect cron list
cc-connect cron edit <job-id> <field> <value>   # e.g. cron_expr, prompt, enabled, mute, timeout_mins
cc-connect cron exec <job-id>
cc-connect cron del <job-id>
```

Необязательный параметр `--session-mode new-per-run` начинает новую сессию ИИ-агента при каждом запуске (по умолчанию используется `reuse`, как и раньше). `--timeout-mins N` задаёт время ожидания планировщика для одного запуска (`0` — без ограничения; если параметр не указан — 30 минут).

### Естественный язык (Claude Code)

> «Каждый день в 6 утра составляй сводку популярных репозиториев GitHub»

Claude Code автоматически создаёт cron-задачу. Для других ИИ-агентов, которые используют файлы памяти, сначала один раз выполните `/cron setup` или `/bind setup`: обе команды записывают одинаковые инструкции.

## Настройка командной оболочки

По умолчанию cc-connect использует `sh` в Unix и `powershell.exe` в Windows для всех запусков команд через оболочку (команды `/shell`, cron-задачи с exec, обработчики и webhook с exec). Можно переопределить эту настройку и использовать другую оболочку.

### Поддерживаемые оболочки

| Оболочка | Значение в конфигурации | Флаг |
|-------|-------------|------|
| sh (по умолчанию в Unix) | `sh` | `-c` |
| bash | `/bin/bash` | `-c` |
| zsh | `/bin/zsh` | `-c` |
| fish | `/bin/fish` | `-c` |
| cmd (Windows) | `cmd` | `/C` |
| PowerShell (по умолчанию в Windows) | `powershell.exe` | `-Command` |
| PowerShell Core | `pwsh` | `-Command` |

Флаг определяется автоматически по имени оболочки — настраивать его вручную не нужно.

### Глобальная конфигурация

Задайте `shell` на верхнем уровне `config.toml`, чтобы изменить оболочку по умолчанию для всех проектов:

```toml
shell = "/bin/zsh"
```

### Переопределение для отдельного проекта

Переопределите оболочку для конкретного проекта:

```toml
[[projects]]
name = "my-project"
shell = "/bin/fish"
```

### Профиль командной оболочки

Используйте `shell_profile`, чтобы добавлять скрипт настройки перед каждой командой оболочки. Это удобно для загрузки профиля оболочки, чтобы были доступны пользовательские функции, псевдонимы и переменные окружения:

```toml
shell = "/bin/zsh"
shell_profile = "source ~/.zshrc"
```

Профиль оболочки и команда пользователя соединяются переводом строки и передаются оболочке единым скриптом, что позволяет избежать проблем с кавычками. Например, `/shell echo $MY_VAR` превращается в:

```zsh
source ~/.zshrc
echo $MY_VAR
```

`shell_profile` также поддерживает переопределение для отдельного проекта:

```toml
[[projects]]
name = "my-project"
shell = "/bin/fish"
shell_profile = "source ~/.config/fish/config.fish"
```

### На какие способы выполнения это влияет

Настройка оболочки применяется ко всем способам выполнения команд в cc-connect:

- **Команда `/shell`** — интерактивные команды оболочки из чата
- **Cron-задачи с exec** — записи `[[cron]]` с полем `exec`
- **Обработчики** — записи `[[hooks]]` с `type = "command"`
- **Webhook с exec** — webhook-запросы с полем `exec`

## Веб-панель управления (Beta)

> **Статус: Beta.** Функция доступна начиная с v1.2.2-beta.5. Интерфейс и API могут измениться в будущих выпусках.

Полнофункциональный интерфейс управления, встроенный в исполняемый файл: создание, просмотр, изменение и удаление проектов (CRUD), управление сессиями, редактор cron-задач, глобальные настройки, интерфейс чата и поддержка разных языков (i18n).

При импорте провайдеров из CC-Switch через панель управления импорт отклоняется, если выбранное имя соответствует нескольким исходным провайдерам. В рамках такого запроса не добавляется ни один провайдер. Снимите выбор с неоднозначного имени, чтобы импортировать остальных провайдеров с уникальными именами.

### Быстрая настройка (команда чата)

Самый простой способ включить веб-панель:

```
/web setup
```

Команда автоматически включает **Management API** и **Bridge** в `config.toml`, генерирует токены и выводит URL для доступа. Чтобы изменения вступили в силу, может потребоваться выполнить `/restart`.

После настройки откройте указанный URL (по умолчанию `http://localhost:9820`) и войдите с помощью токена.

### Проверка состояния

```
/web           # or /web status — show current web admin URL and status
```

### Ручная настройка

Добавьте в `config.toml`:

```toml
[management]
enabled = true
port = 9820                     # Management UI & API listen port
token = "your-secret-token"     # Login token; /web setup generates one automatically
cors_origins = ["*"]            # Allowed CORS origins; empty = no CORS headers
```

Затем перезапустите cc-connect.

### Параметры сборки

По умолчанию ресурсы веб-интерфейса включаются в исполняемый файл при сборке. Чтобы исключить их (экономия примерно 1 МБ):

```bash
make build-noweb
# or
go build -tags 'no_web' ./cmd/cc-connect
```

При сборке с `no_web` команда `/web` сообщает, что веб-панель управления недоступна.

### API управления

Management API обслуживается на том же порту, что и интерфейс. Базовый URL: `http://<host>:<port>/api/v1`

Все API-запросы требуют заголовок `Authorization: Bearer <token>`.

Основные конечные точки:

| Метод | Путь | Описание |
|--------|------|-------------|
| `GET` | `/api/v1/status` | Состояние системы (версия, время работы, платформы) |
| `POST` | `/api/v1/restart` | Перезапустить cc-connect |
| `POST` | `/api/v1/reload` | Перезагрузить конфигурацию |
| `GET` | `/api/v1/projects` | Получить список проектов |
| `GET` | `/api/v1/sessions?project=<name>` | Получить список сессий проекта |
| `GET` | `/api/v1/cron` | Получить список cron-задач |
| `GET` | `/api/v1/settings` | Получить глобальные настройки |
| `PATCH` | `/api/v1/settings` | Обновить глобальные настройки |

Полный справочник API: [management-api.md](./management-api.md)

## Bridge — подключение внешних адаптеров (Beta)

> **Статус: Beta.** Функция доступна начиная с v1.2.2-beta.5. Протокол может измениться в будущих выпусках.

Bridge предоставляет сервер WebSocket + REST, через который внешние адаптеры (собственные интерфейсы, боты, скрипты) могут взаимодействовать с сессиями cc-connect: отправлять сообщения, получать события и управлять сессиями.

### Включение через чат

Команда `/web setup` автоматически включает Bridge вместе с Management API.

### Ручная настройка

Добавьте в `config.toml`:

```toml
[bridge]
enabled = true
port = 9810                     # Bridge listen port (separate from management)
token = "your-bridge-secret"    # Auth token for WebSocket and REST
path = "/bridge/ws"             # WebSocket endpoint path
cors_origins = ["*"]            # Allowed CORS origins; empty = no CORS
```

Затем перезапустите cc-connect.

### Аутентификация

Для всех подключений к Bridge необходим токен. Поддерживаемые способы передачи:

- Параметр запроса: `?token=<bridge-token>`
- Заголовок: `Authorization: Bearer <bridge-token>`
- Заголовок: `X-Bridge-Token: <bridge-token>`

### WebSocket

Подключитесь к:

```
ws://<host>:<bridge-port>/bridge/ws?token=<bridge-token>
```

WebSocket поддерживает двусторонний обмен сообщениями: отправляйте сообщения пользователя ИИ-агенту и получайте его события (текст, вызовы инструментов, запросы разрешений и т. д.) в реальном времени.

### REST API

Обслуживается на том же порту, что и WebSocket.

| Метод | Путь | Описание |
|--------|------|-------------|
| `GET` | `/bridge/sessions?session_key=...&project=...` | Получить список сессий |
| `POST` | `/bridge/sessions` | Создать новую сессию |
| `GET` | `/bridge/sessions/{id}?session_key=...&project=...` | Получить сведения о сессии и её историю |
| `DELETE` | `/bridge/sessions/{id}?session_key=...&project=...` | Удалить сессию |
| `POST` | `/bridge/sessions/switch` | Переключить активную сессию |

Полный справочник протокола: [bridge-protocol.md](./bridge-protocol.md)

### Сводка портов

| Сервис | Порт по умолчанию | Блок конфигурации |
|---------|-------------|--------------|
| Управление (веб-интерфейс + API) | 9820 | `[management]` |
| Bridge (WebSocket + REST) | 9810 | `[bridge]` |

## Часто задаваемые вопросы

Краткие ответы на вопросы, которые неоднократно возникали в обсуждениях задач и были решены сопровождающими проекта. Каждый пункт содержит ссылку на исходную задачу или PR, чтобы при необходимости можно было изучить подробности.

### Поддерживает ли cc-connect OpenClaw? (задача #501)

Да. OpenClaw поддерживается через [Agent Client Protocol (ACP)](https://agentclientprotocol.com/get-started/agents). В cc-connect есть тип ИИ-агента `acp`, который взаимодействует с любым ACP-совместимым CLI, включая подкоманду `openclaw acp` в OpenClaw.

Минимальный фрагмент конфигурации (полная версия находится в `config.example.toml` под заголовком `# --- Example: OpenClaw (Gateway-backed ACP bridge) ---`):

```toml
[[projects]]
name = "openclaw-acp"

[projects.agent]
type = "acp"

[projects.agent.options]
work_dir = "/path/to/project"
command = "openclaw"
args = ["acp"]
display_name = "OpenClaw ACP"
```

**Для удалённых шлюзов требуется сопряжение.** Если вы направляете cc-connect на удалённый OpenClaw Gateway (`args = ["acp", "--url", "wss://..."]`), сначала необходимо выполнить сопряжение, иначе все ответы будут пустыми:

1. Запустите шлюз: `openclaw acp --url wss://your-gateway:18789`
2. В другом терминале выполните: `openclaw pair`
3. Подтвердите запрос сопряжения в интерфейсе OpenClaw
4. Теперь cc-connect может взаимодействовать с авторизованным шлюзом

Пустые ответы OpenClaw почти всегда означают, что пропущен шаг сопряжения (задача #432). Прежде чем искать другие причины, повторно выполните `openclaw pair` и снова подтвердите сопряжение. Источник: <https://zhuanlan.zhihu.com/p/2005687480976970296>

### Групповой чат личного WeChat — поиск правильного `chat_id` (задача #805)

Личный WeChat (платформа `weixin`) поддерживает групповые чаты. Чтобы привязать бота к определённой группе, задайте в `chat_id` секции `[[projects.platforms.options]]` **идентификатор группового чата**, а не отдельного пользователя. Идентификаторы групповых чатов всегда заканчиваются на `@chatroom`, например:

```toml
[[projects.platforms]]
type = "weixin"

[projects.platforms.options]
token = "ilink_bot_bearer_token"
chat_id = "your_group_chat_id@chatroom"   # group chats end with @chatroom
```

**Как найти идентификатор группового чата:**

1. Запустите cc-connect и убедитесь, что бот находится в нужной группе.
2. Отправьте в группу любое сообщение с аккаунта, которому заведомо разрешён доступ.
3. Проверьте журналы cc-connect: входящий `chat_id` (с окончанием
   `@chatroom`) записывается в момент получения сообщения. Скопируйте
   это значение в `chat_id`.

Оставьте `chat_id` пустым (или не указывайте ключ), чтобы бот отвечал во всех чатах, в которых состоит. Укажите конкретное значение, чтобы ограничить ответы только этой группой или пользователем.

Частые затруднения:

- **«Как добавить бота в группу?»** Ботов личного WeChat добавляют,
  сканируя QR-код *внутри* группы с привязанного аккаунта WeChat
  либо передавая QR-код через личный чат и затем открывая его
  внутри нужной группы. В API нет вызова «пригласить бота в группу»;
  бот становится участником группы так же, как любой другой
  контакт WeChat.
- **Бот совсем не получает сообщения группы** — убедитесь, что группа привязана
  к вашему экземпляру cc-connect. Если задан `allow_from`, фиксируется первый пользователь,
  отправивший сообщение в группу; если привязка относится к другому пользователю,
  бот не отвечает.
- **Бот отвечает в личном чате, но игнорирует группу (или наоборот)** —
  продублируйте блок `[[projects.platforms]]`: в одном задайте `chat_id`
  группы, а во втором не задавайте его, чтобы охватить оба варианта общения.

Подробнее о платформе `weixin` см. [docs/weixin.md](./weixin.md).

### Прокси Telegram / ограничения исходящих соединений (задача #245)

Платформа Telegram напрямую поддерживает HTTP- и SOCKS5-прокси для исходящих соединений через `[projects.platforms.options]`. Общесистемный прокси или отдельный вспомогательный сервис (sidecar) не нужны: задайте прокси для конкретного экземпляра Telegram.

```toml
[[projects.platforms]]
type = "telegram"

[projects.platforms.options]
token = "${TELEGRAM_BOT_TOKEN}"
proxy = "http://127.0.0.1:7890"     # or socks5://127.0.0.1:1080
proxy_username = ""                  # leave empty if no auth
proxy_password = ""
```

`proxy` принимает URL с `http://` и `socks5://`. Аутентификация необязательна. Прокси влияет только на вызовы Telegram Bot API этого экземпляра платформы; трафик других платформ и API управления через него не направляется.

Полный справочник: [docs/telegram.md](./telegram.md#21-optional-use-a-proxy).
Этот параметр добавлен в PR #389.
