# CC-Connect Team：复用原有能力，按项目群协作

[飞书方案](https://bytedance.larkoffice.com/docx/L67kdCJp5oUt0AxZ7VocQq4JnIt) · [实施计划](plans/agent-team-implementation.md) · [配置示例](../config.agent-team.example.toml)

使用普通 `[[projects]]` 配置 Bot 运行实例，通过可选 `[[teams]]` 组织成员和角色。每个业务项目创建一个新飞书群，管理者自动加入。同一 Bot 可以参加多个项目群，按消息所在群自动选择上下文。本文描述当前运行能力；历史版本和交互原型见[原型索引](prototypes/team-interaction/README.md)。

## Team、Project 与 Workspace

Codex 的 `full-auto` 使用工作区写入沙箱并关闭逐次审批，不等同于全盘或网络访问。需要工具凭据刷新时，可在相应 Bot 的 `projects.agent.options` 显式配置 `sandbox_writable_roots = ["/绝对路径/凭据缓存"]`；需要联网时配置 `sandbox_network_access = true`。默认不增加权限，这些运行目录不进入项目源码目录列表，切换项目不会覆盖它们。只调整这两项不会清空成员的既有上下文。

运行时的 `CC_DATA_DIR` 指向服务控制 API 所在目录，与成员历史数据的 `contexts/...` 目录分开；`team status` 等命令使用前者的 `run/api.sock`。

- **Team（团队）**：可复用的 Bot 成员、角色与身份配置，入口 `/team`。
- **Project（项目）**：一个具体目标、一个独立项目群、参与成员和目录关联，入口 `/project`。同一 Team 可以承接多个 Project。
- **Workspace（工作目录）**：底层 Agent 实际读写代码的目录，作为项目设置中的“代码目录”展示。项目群内 `/workspace`、`/dir` 都打开统一项目设置；未关联项目的会话继续沿用原生行为。

例如同一 Team 同时做 shop 和 payment 两个 Project，各有自己的群和工作目录。Project 也可以引用相同目录，但 Bot 会话和模型覆盖仍按项目隔离。项目数据与 Team 成员配置分开保存，项目通过 Team ID 和 Bot 引用选择人员。

`/help` 现在只返回一张原生帮助卡片，“团队管理”和“项目管理”与原有四组命令并列；不再额外发送独立 Team 说明。不支持卡片的平台合并为一条帮助消息。旧 `/team projects`、`/team project create ...` 及对应 CLI 入口保留兼容，新操作使用 `/project`。为了兼容 cc-connect，配置文件中的 `[[projects]]` 仍表示原生 Bot 运行实例，不改名、不迁移已有会话。

## 构建和安装

```sh
make build-team
make test-team
```

产物 `dist/cc-connect-team` 包含原有全部后端、消息平台和 Web 功能。`agent_team` 标记不再用于裁剪功能；原有可选编译标签仍可单独使用。原有 `/help`、`/model`、`/mode`、`/reasoning`、`/list`、`/new`、`/history`、`/workspace`、`/cron` 等命令沿用现有处理逻辑、权限和后端能力判断，不设置 Team 专用命令白名单。

首次使用，在本机终端执行（预先安装并登录所选后端 CLI）：

```sh
./dist/cc-connect-team team init --agent codex --work-dir "$HOME/Workspace"
```

`--agent` 支持 `codex`、`claudecode`、`trae`，与 manager 角色独立。扫码创建应用、绑定扫码用户为管理员、保存配置、启动服务连续完成。无需手填 App Key、open_id 或发送 `/new claim`。应用扫码注册与授权读取个人文档的用户 OAuth 不同；运行时仍持有每个 Bot 自己的应用凭据。应用发布、可用范围和租户审批仍受飞书设置约束。

`--config` 指定尚不存在的配置文件，`--id` 指定 Bot 名称，`--qr-image` 保存二维码，`--timeout` 指定等待秒数，`--no-start` 只保存配置。再次启动直接使用 `cc-connect-team --config /path/config.toml`，无需重新注册。扫码只在本机终端或私聊中进行，不在群聊展示授权链接。

## Team 配置

保留已有的 `[[projects]]`、`projects.agent`、`projects.platforms` 和所有原生配置；仅追加：

```toml
[[teams]]
id = "default"
manager = "manager-main"
auto_coordinate = true

[[teams.members]]
bot = "manager-main"
role = "manager"
prompt = "使用中文沟通，理解需求并组织项目。"

[[teams.members]]
bot = "developer-a"
role = "developer"
prompt = "提交修改说明与实际测试结果。"
```

`bot` 引用普通 `projects.name`，示例中两个 Bot 都必须已经有对应运行配置。角色只描述职责，后端仍配置在各自 `projects.agent` 中。Codex、Claude Code、Trae 都可以承担任一角色；五类内置角色为 manager / planner / developer / tester / reviewer。首版一个 Bot 只能属于一个 Team，但可参加该 Team 内多个项目。Team 必须引用一个 manager 成员。

新增 Bot：在与管理者的**私聊**中发送：

`/team bot create` 打开填写卡片，也可以点击 `/help` 中的对应入口。选择角色和执行后端，身份说明选填。创建表单不包含 Bot 名称；内部标识在打开表单时自动生成，不展示也不允许修改，表单重试保留同一标识。

Bot 名称在飞书注册页面设置，扫码完成后读取飞书实际名称用于展示。群聊不提供 Bot 注册表单或扫码链接。

完整参数命令仍然可用：

```text
/team bot create developer-a developer codex
/team bot create reviewer-a reviewer claudecode 遵循项目验收标准进行审查
/team bot create tester-a tester trae
```

完成扫码后保存普通运行配置、Team 成员信息和所有者，随后启动新 Bot。后端 CLI 不可用时保留配置并报告连接失败，安装登录后重启即可，不必重复创建应用。手动创建的新 Bot 不会追加入已存在的项目群；自动协调中的 `ensure-role` 会核验后加入请求它的项目群。

`/team members`（Help → Team → Members）展示飞书名称、角色和执行后端。点击“修改”，打开与创建 Bot 共用的配置表单，预填角色、执行后端和身份说明，额外只读展示飞书名称；底部按钮为“修改”，创建表单底部为“创建”。角色、执行后端和身份说明可以修改，管理者的角色固定；保存后重启服务生效，适用于该 Bot 参与的所有项目。飞书名称不可在卡片内修改；后台更新名称后重新打开 Members 读取。提交内容不能修改名称或内部标识。其他 Bot 的 Members 仅展示成员列表。

飞书名称只作展示，修改名称不会改变 Bot 内部标识、项目关联或会话路径。角色修改保留原有后端参数；切换后端沿用已有规则，清除原后端专属参数。原来的 `member set` 命令已移除。

## 个人会话标签

在与管理者的**私聊**中打开 `/help → 团队管理 → 标签设置`，或发送 `/team labels`。分别设置“新建 Bot 的标签”和“新建任务群的标签”：可多选已有普通标签，也可每行填写一个新标签名（每类最多 10 个）；保存的默认值立即用于后续创建。同名普通标签会复用，存在多个同名标签时需在列表中选择明确的标签。规则标签由飞书规则管理，不在选择列表中。

点击“授权标签管理”完成一次用户身份授权；管理者应用需开通**用户身份**权限 `im:feed_group_v1:read`、`im:feed_group_v1:write`，自动续期还需 `offline_access`。应用身份权限不能替代用户授权。群聊只提示转到私聊，运行时校验扫码账号与发起人的 open_id 一致后保存凭据。凭据按应用和用户隔离，保存在数据目录下权限为 0600 的文件中；不会修改 Agent CLI 或 lark-cli 的凭据。

创建 Bot / 项目群的表单会带入默认标签，允许本次替换、添加或清空；清空选择及新标签名表示本次不添加。直接使用完整参数命令和管理者自动创建角色时也使用默认值。新 Bot 使用自身应用对应的所有者 ID 发送一条欢迎消息以建立私聊，再由管理者已授权的用户身份将该会话归类；此步骤需要新 Bot 的 `im:message:send_as_bot` 权限。标签仅影响授权用户自己的会话列表。

添加失败不会撤销或重复创建 Bot / 项目群。原目标、标签与进度会持久化；授权或权限恢复后，在标签设置点击“重试待添加标签”，或私聊发送 `/team labels retry`，只补标签。服务重启后仍可重试；已完成的标签任务跳过。更改默认值只影响后续创建，已有待重试任务保留原选择。

## 项目群

在管理者对话里使用：

`/project create` 打开一张完整的创建表单，包含项目名称、项目目录、其他成员和项目目标，管理者自动加入。项目名称支持中文、空格和大小写，新建群使用完全相同的名称。内部标识由系统自动生成，不出现在表单里，也不能通过表单修改；失败重试沿用同一个标识，避免重复建群。项目列表和创建结果显示项目名称。项目目录为必填文本框，默认带入当前会话的实际工作目录（与 `/dir` 的上下文一致），可以直接修改或粘贴绝对路径，无需逐层浏览。

表单中的目录按一个完整路径处理，支持空格、中文和逗号，无需加引号。点击“创建”后校验并沿用原有创建流程，不存在的目录会自动建立。创建失败后保留目录和其他已填内容，便于修正后重试。

完整参数命令仍然可用：

```text
/project create shop /absolute/path/to/shop
/project create payment /absolute/path/to/payment developer-a,reviewer-a 完成支付接口和测试
/project list
```

目录参数包含空格时使用双引号。不指定成员则使用当前 Team 全部成员；指定时始终自动包含管理者。多目录以逗号分隔，只有所有参与后端都支持时才允许；Claude Code、Codex（exec / app_server）及 Trae ACP 均已接入；其他后端必须声明支持，不能静默忽略附加目录。

管理者也获得了对应本地 CLI 的使用说明，可根据自然语言请求调用：

```sh
cc-connect-team project --config /path/config.toml --manager manager-main create shop /absolute/path/to/shop developer-a,reviewer-a "完成订单服务"
cc-connect-team project --config /path/config.toml list
```

创建卡片使用飞书 Card 2.0，填写后一次提交；可返回的菜单、列表、表单及结果页统一使用 2.0，避免从表单返回时降级为 1.0 被飞书拒绝。独立的旧版卡片继续沿用已有渲染。表单引用绑定发起人和原聊天，30 分钟有效；重复提交不会重复执行，服务重启后需重新打开表单。服务器校验字段和管理权限，创建失败会在原卡片显示保留填写内容的重试表单，使用相同标识重试仍走原有恢复流程。不支持表单的平台继续显示文本命令用法。

### Help 卡片导航

发送 `/help` 后，分类切换、原生命令页面、Team / Project 页面、Members 配置和创建表单都在这条卡片消息内切换。页面底部提供“返回”；表单返回无需填写必填项，返回后旧表单失效，再次打开会获取新的表单。提交结果或失败提示也更新原卡片，失败时保留已填写内容。

管理页面沿用 cc-connect 的蓝色标题、列表操作、按钮及分隔线样式。创建与修改继续复用同一 Bot 配置表单：创建不填写名称或内部标识，Members 中的飞书名称只读。

直接输入命令仍按原有方式回复。多张 Help 卡片分别导航，较晚完成的旧页面及文本回复不会覆盖新页面或另发消息。卡片触发的主动回复、状态页和异步结果也更新原消息；飞书拒绝更新旧卡片时会发送替代卡片。升级后请重新发送 `/help` 获取新导航卡片。群聊中的同一张卡片由群成员共享当前页面，表单提交仍限于发起人。

建群过程先保存项目 ID、重试 UUID 和计划，再创建群、加入成员、核验管理者、标记就绪，返回群链接。中途失败时，使用完全相同的项目 ID 和参数重试，会继续配置原群。同名项目参数冲突会报错。飞书权限、跨租户 Bot、成员不可见或待审批会明确报错，不会报告虚假的完成。

进入项目群并 @ 对应 Bot 即可工作；不需要手动切项目或 `/bind`。群内话题继承项目目录；同一项目的同一成员跨话题持续使用一个模型会话，公开消息仍回复到各自话题。私聊管理者保留独立的管理会话。一个项目只能绑定一个群；创建新项目会创建新群。

未开启自动协调时，Bot 之间可使用 cc-connect 原生 relay 交接任务，由项目成员表自动提供绑定。开启后由管理者使用下述 `team dispatch`，普通聊天审批继续生效。直接转交和定时任务启动前检查管理者仍在群里；缺失时停止该次自动执行并报错。当前没有自动重新邀请管理者或管理者退出事件的后台巡检；任务总览通过 `/project board` 查看。普通用户交互和恢复操作不受此检查影响。

## 统一项目设置

进入项目群，发送 `/project` 或 `/project settings`。卡片显示当前项目的目标、Team、管理者、参与成员和代码目录，提供“编辑项目信息”“修改代码目录”“查看成员”“Bot 设置”按钮。Help → 项目管理 → 项目设置 → 修改代码目录打开主目录、附加目录表单。主目录是命令执行时的工作目录；附加目录每行一个已有绝对路径，可包含空格和逗号。清空附加目录字段会移除全部附加目录。表单返回和提交结果更新同一张管理卡片。文字命令也可使用：

```text
/project name 商城
/project goal 完成订单服务
/project directory
/project directory /absolute/path/to/shop
/project directories add /absolute/path/to/backend
/project directories remove /absolute/path/to/backend
/project directories clear
/project bot
/project model reset
```

目录只保存一份有效项目配置。`/workspace route <绝对目录>`、`/workspace bind <目录名>`、`/dir <绝对目录>` 在项目群内都走同一更新流程，作用于该项目的所有 Bot；旧 `/dir` 卡片也会返回项目设置，不会写入第二份覆盖值。项目群的 `/help` 不再重复列出 `/workspace` 和 `/dir`，普通会话仍保留。

修改主目录、附加目录或项目目标前检查所有在本服务运行的项目 Bot，存在任务、派工、定时执行或 shell 任务时拒绝修改。修改后启用新的上下文版本，关闭旧的空闲交互会话，原会话文件保留；重新选择以前的目录也不会自动续接旧任务。项目名称修改不重置上下文。只接受已存在的绝对目录，重复路径与软链接别名会合并。单独修改主目录的旧命令仍保留附加目录；整个目录表单一次性保存。旧版本表单提交会被拒绝，需重新打开，防止覆盖较新的设置。目录修改不改变审批模式。

旧项目若存在不同的 Workspace 路由或话题目录覆盖，设置卡片列出项目目录与旧目录，执行暂停并提示使用 `/project directory <绝对目录>` 明确选择。旧文件保留供恢复，完成选择后不再参与此项目的目录路由。新建项目直接使用统一配置。

“Bot 设置”针对收到命令的 Bot，显示后端、当前模型及来源（继承 Bot 默认值 / 当前项目覆盖）。修改模型复用 `/model`，`/project model reset` 清除本项目覆盖并恢复 Bot 当前默认值。账号、执行平台、Team 身份等共享配置明确标记影响该 Bot 的所有项目；修改仍走管理者私聊或原生配置。成员按钮目前查看项目成员及共享身份说明，不在此页调整群成员。

后台任务默认使用项目目录。任务显式指定其他目录时会报冲突，需要修改任务目录或明确修改项目目录，避免绕过统一设置。现有服务须统一升级，不应让旧版本进程同时修改这些状态文件。

## 上下文和原生命令

运行实例和会话存储按 Bot、项目及上下文版本隔离。同一项目的同一 Bot 跨任务和话题共享持续模型会话；不同项目群即使共用目录，也有各自的模型覆盖和历史索引，重启后恢复。非项目会话保留原生用户/话题规则。Team 下 `/list`、`/switch` 等只操作当前上下文已知的原生会话，避免自动导入别的项目或终端会话。

项目群里的 `/model`、模型卡片、`/mode` 和 `/reasoning` 操作当前项目的 Agent。模型覆盖持久化；mode/reasoning 的持久化能力沿用原生行为。`/lang`、provider、`/reload` 等原有全局或 Bot 配置项仍采用原生作用域，不能据此认为每个配置都变成了项目级。

上下文隔离不是文件或账号权限隔离。两个 Bot 同时改同一仓库仍需安排分工或使用独立 worktree；当前不提供自动合并和文件冲突解决。角色说明注入到适配器，不修改共享仓库的 AGENTS.md / CLAUDE.md。任务支持持久化计划、依赖验收和显式返工；后续派工由管理者判断并执行，不是自动重试调度器。

## 从实验 v2 升级

旧 `[[bots]]` 和 `business_projects` 兼容路径暂时保留。切换到新的 Team 运行方式：

```sh
cc-connect-team team adopt --input /path/old.toml --output /path/new.toml
```

此命令只写新的 0600 配置文件，不覆盖输入；保留凭据占位符，并通过 `session_data_dir` 指向旧 Bot 的会话目录，避免管理员私聊历史丢失。核对后替换服务配置并重启。已有 `business_projects` 的配置必须先确定项目群映射，工具会拒绝猜测迁移，不会自动删除旧项目或历史。新配置不再使用 `/project use`，也不会触发旧 v2 的命令限制。

## 验收步骤

1. 在管理者私聊运行 `/help`，确认只出现一张卡片，团队管理、项目管理与原生命令同页导航；分别点击 `/team members`、`/project list`。再运行 `/model`、`/status`，确认原生命令可用。
2. 创建项目 A，收到新群链接，群内包含用户、管理者及选定成员；在群内 @ Bot 执行 `/workspace`。
3. 用同一 Bot 创建项目 B。A 修改模型并对话后，在 B 查看模型及历史，再回 A 核验；无需项目切换命令。
4. 在项目群开启两个话题，核验话题沿用群目录；操作模型、模式和推理卡片。
5. 重启服务，回原群核验模型、会话索引和原生续接；新建成员扫码后核验角色与后端分别生效。
6. 重试同一建群请求，核验没有重复建群；移除管理者后尝试 relay / 定时执行，核验明确失败。

自动化验证包含配置兼容、模拟飞书建群与部分失败、同目录跨群跨 Bot 隔离、原生会话过滤、卡片作用域、自动任务管理者检查、重启恢复和 ReceiveMessage 驱动的用户旅程。真实飞书群创建、多 Bot 执行及各后端账号可用性仍需现场验收。

### 人工审批

Team 初始化、新建成员和切换后端时，默认启用人工审批：

| 后端 | 配置 | 审批传输 |
| --- | --- | --- |
| Codex | `backend="app_server"`、`mode="suggest"` | app-server 双向请求与响应 |
| Claude Code | `mode="default"` | stream-json `can_use_tool` / `control_response` |
| Trae | `cmd="traecli"`、`args=["--permission-mode", "default", "acp", "serve"]` | ACP `session/request_permission` |

Agent 请求权限后，桥接会在当前回复卡片上展示审批按钮，等待用户允许或拒绝，再把结果返回同一个会话。权限模式决定哪些操作需要审批，并非每条命令都会弹卡：Codex 的 `suggest` 使用只读沙箱和 `on-request`；Trae 的 `default` 允许工作区内读写与执行，需要联网或访问工作区外的受限资源时请求审批；Claude Code 按其原生权限规则执行。

Trae 在启动时显式使用审批参数，`/mode` 则按当前 ACP 服务端公布的模式切换。当前本机版本已验证提供 `default`、`plan`、`auto`、`bypass_permissions` 四个选项；其中 `auto` 使用自动审批，`bypass_permissions` 跳过审批，需要人工审批时选择 `default`。Codex 的 `exec` 后端没有审批回传通道，必须使用 `app_server`。

编辑已有成员的名称、角色和提示词会保留其权限设置；切换后端或新建成员会使用上表默认值。已有部署需相应修改配置并重启服务。后台任务或旧 relay 沿用各自权限处理规则。自动协调项目禁用旧 relay，管理者派工通过普通聊天通道接收审批。

### 每次请求分为过程卡和结论卡，超长自动续卡

Team 初始化和新建 Bot 默认开启飞书平台选项 `single_card_reply = true`、`separate_final_card = true`（同时要求 `enable_feishu_card = true`，后者默认开启）。已有 Bot 可在各自的 `[projects.platforms.options]` 中设置并重启服务；普通非 Team 配置默认保持原有行为。仅开启 `single_card_reply` 时过程与答案仍合并，但同样支持超长自动续卡。

过程卡在出现需要展示的公开进展、工具操作、审批或问题后创建并持续更新；当前动作和结束状态放在底部，不在顶部展示通用“执行中”。完成后单独交付渲染 Markdown 的结论，已有过程卡保留供回看。只有最终答案时直接交付结论，没有展示内容的回合不创建空卡；临时等待卡在结束时为空则撤回。普通回复不自动 @ 人类发起人，机器人任务交接仍保留结构化 mention。`/stop`、`/cancel` 和执行错误在过程卡结束，不另发结论卡。等待队列和后台自动压缩不另发通知。

内容按约 3000 字符的容量自动续发为新卡片，不再显示“上一页 / 下一页”按钮。已有分段继续复用原消息，只有超过容量才创建后续卡片；代码块跨卡时会补齐围栏，避免格式断裂。过程和结论分别续卡，审批、提问和队列提示只放在当前过程卡上，完成后移除审批按钮。输出修订变短时，已经发布的多余分段保留为历史并标明“请以更新后的结果为准”。文件与语音附件仍作为附件发送，菜单命令保持各自交互。设置优先于正文预览和进度卡模式；显示思考/工具过程仍遵循 `display` 设置。

旧版本已经发出的分页卡继续保留回调兼容及原有私有快照（0600、按应用与实例隔离，最多 256 条、24 小时）；不会自动重新发送历史消息。新卡片直接在聊天记录中阅读，不依赖翻页回调或本地分页快照。

过程卡更新失败不阻止结论卡发送；续卡重试复用已成功发送的消息。结论卡创建失败时尝试用已有过程卡显示未送达的结论分段，容纳不下时明确提示部分内容未送达。首次创建过程卡失败时回退原有发送路径。审批按钮绑定当前问题的随机标识，旧按钮和重复点击不会批准下一项操作。

### ACP 模型与推理配置

ACP Bot 的 `/model`、`/reasoning` 和 `/mode` 使用 Agent 返回的会话配置，首次聊天前即可打开。优先读取 `configOptions`，按 `model`、`thought_level`、`mode` 分类；保留旧版 `models` / `modes` 的兼容路径。没有提供的能力会明确提示不支持，不显示空选择框。

切换选项使用 `session/set_config_option`，服务端确认后才显示成功。返回值及 `config_option_update` 都按完整配置快照处理，切换模型可能移除或重置推理强度。卡片提交稳定的选项值，避免旧卡片的序号指向新的选项。服务端拒绝时保留原设置；模型配置保存失败会尝试恢复原模型与推理强度。

配置发现会按需预建一个不发送 prompt 的 ACP 会话，反复打开菜单复用它，下一次新对话也可直接使用；停止 Agent 或变更目录/运行环境时回收连接。模型和推理偏好会在后续新建或恢复的 ACP 会话中应用。ACP 配置切换保留会话 ID 和聊天历史；Claude Code、Codex 等原有后端的命令语义保持原样。模型仍通过现有模型配置保存路径持久化，推理强度沿用运行时设置语义。

本机 Trae CLI 0.205.1 验证：19 个模型；部分模型提供 `low/medium/high/xhigh` 推理选项；以显式审批参数启动后，返回上述 4 个权限模式。不能据此把 `/provider` 或 `/memory` 视为已支持。

本地集成验证（需要已登录 Trae，不发送模型任务，结束后删除本次临时会话）：

```bash
CC_ACP_TRAE_INTEGRATION=1 go test ./agent/acp -run '^TestTraeACPConfigIntegration$' -v -count=1
```


### 管理者自动协调

执行类请求由管理者通过 `team dispatch` 分派给适合的项目成员，并根据产物推进下一阶段；仅在派工命令成功后报告已分派。管理者不以自己开发或本地子代理代替现有团队成员，除非用户明确指定由管理者执行。Codex 恢复已有会话时，在每次运行连接的首次发送重新注入当前角色和成员配置，保留会话历史；同一连接的后续轮次不重复注入。服务重启后无需删除会话才能获得新的分派指令。

管理者按当前请求的范围、不确定性和影响选择流程。本地提交已有成果、创建 worktree、整理已有产物等范围明确的操作，默认一个任务交给熟悉仓库的开发者，完成前置检查、执行和自检，再由管理者检查关键证据并一次验收。该成员忙时先保存为计划，不能仅因其他成员空闲就转交。多个仓库或文件较多本身不触发独立审查；只有具体疑点、缺陷、实质风险、强制要求或用户明确要求，才增加规划、审查或测试角色。必要的仓库规则和权限仍须遵守。

提交验收聚焦实际提交、纳入范围及原有无关改动保留；worktree 验收聚焦目录、分支、HEAD、注册关系及原工作区保留。管理者不默认重复整套命令、逐文件哈希、无关缓存清单或旧测试；完成条件满足后结束，不额外派发“再验证一次”。这是模型的编排指引，不是放宽运行时权限或强制跳过验证的开关。

接口清单、参数说明、资料梳理等任务以成员原稿为交付。管理者检查是否覆盖用户问题、内容是否一致、关键结论是否有来源；已有完整且有依据的答案时，直接验收，不默认再次通读源码或重做接口梳理。发现具体缺项、矛盾或必须核验的事实时，只补查对应部分，或请原成员定向补充；验收依据必须如实说明检查的是原稿还是源码。

成员原稿已在群内发布且没有新决策时，管理者完成验收后使用 `NO_REPLY`，不再发布第二份表格、缩写稿或“重新整理”的进度。需要补充时只说新增结论、修正、阻塞或下一步，并引用原交付。运行时会在结果通知中明确原稿是否已发布；未确认发布时，不能静默丢掉用户唯一的答案。用户明确要求汇总或多个不同结果确需整合时，才另行输出综合稿。

`teams.auto_coordinate = true` 开启项目群协调，新建 Team 默认开启；已有配置需添加后重启。作用域为已配置就绪且包含该管理者的项目群，私聊及其他群保持原行为。项目创建者未 @ 任何人的消息由管理者处理；其他群成员必须通过飞书的真实 @ 明确点名对应 Bot，否则静默忽略，不触发模型或命令。纯文本写 `@名字`、@所有人、旧话题中的附件或文字决策回复都不能替代直接 @；明确 @ 成员仍交给对应成员，并继续检查原有访问权限。管理者应用必须开通并发布 `im:message.group_msg`，否则飞书不会推送未 @ 的用户消息；Bot 结果使用服务内通道，不依赖 Bot 群消息推送。

成员完成一轮、失败、停止、等待审批或等待用户输入时，运行时把来源、状态和结果传给管理者。最新状态保存在项目数据中，管理者自身的回复不会再次触发自己。管理者根据已授权目标、产物和验收证据决定继续派工、处理阻塞或等待用户；“一轮结束”不等于工作验收通过。这是由管理者判断推进的流程，不是确定性依赖调度器。服务重启将未结束状态标记为 interrupted，不自动重放任务。

管理者在项目上下文使用 CLI（自动注入当前 Bot 和会话）：

```sh
cc-connect-team team status
cc-connect-team team dispatch --to <成员内部 ID> --title '实施方案' --reason '方案已验收' --deliverable '补丁和验证结果' --message '读取方案路径，实施指定范围并报告验证结果'
cc-connect-team team ensure-role --role tester --backend codex --reason '验证动态挂载和卸载，交付回归测试报告；当前团队缺少测试者'
```

派工异步执行，成员仍通过原有审批卡等待用户授权。已在排队、执行或等待输入的成员会拒绝重复派工。旧同步 relay 在自动协调项目中禁用，避免跳过普通聊天审批。状态同时保存稳定任务记录和各成员最新进展；任务编号贯穿派工、交付和验收。

`ensure-role` 优先复用当前项目或团队已有的同角色 Bot；需要新应用时只向管理者所有者私聊发送扫码授权。等待授权时不会把角色报告为就绪，完成授权、角色配置、启动和群成员核验后才加入项目成员表并通知管理者继续派工。未通过飞书权限、发布、可用范围或群成员核验时报告失败，保留可重试的注册状态。此功能不会替用户批准租户权限，也不会自动补装缺失的后端 CLI。

邀请入群由管理者执行；确认入群时，管理者和新角色分别使用自己的应用身份查询自身是否在群内。新角色的校验只创建 API 客户端，不启动额外的消息监听。已创建但尚未完成项目接入的角色可以重试同一条 `ensure-role` 命令，复用已有应用和授权；校验失败不会登记成员，重复成功也不会增加重复成员。

新建角色必须提供 `--reason`（1–2000 字），说明需要该角色的原因、具体任务与预期交付。缺少说明时不会发起注册。授权通知会显示项目名称和 ID、角色、执行后端、用途、权限用途及授权后加入现有项目群的动作；授权等待超时或创建失败也会保留这些上下文。已有角色的复用不要求重新授权。

### 失败原因与停止任务

成员失败会把具体诊断送回管理者。Trae 在仓库密级不被所选模型支持时，可能只返回 ACP `Internal error`；适配器会识别同一轮进程日志中的 L4 模型策略错误（4037），向用户和管理者说明应选择组织批准、支持 L4 仓库的模型后再重试。不会自动切换模型，也不会通过重复重试绕过策略。

停止某个成员：在任务所在群和话题中，真实 @ 对应 Bot 并发送 `/stop`。它停止该 Bot 当前会话的执行，丢弃该会话尚未处理的排队消息，保留会话历史；不影响其他成员。`/cancel` 还会清空该会话历史并创建新会话，不适合作为仅暂停工作的默认入口。

项目群管理员使用 `/project pause` 暂停整个项目，使用 `/project resume` 恢复接收新任务。暂停状态持久化，阻止自动派工与旧回报唤醒；恢复不会重派旧任务。单独停止管理者仍不等于暂停项目。详见下方“项目级暂停与恢复”。


## 创建角色时的默认权限

`team init` 创建管理者，以及私聊创建成员、管理者自动补充测试者等角色时，都会在保存 Bot 后检查该应用的角色权限。申请失败不会丢失已创建的应用、重新注册 Bot 或影响已保存的凭据。

| 角色 | 默认权限范围 |
| --- | --- |
| 全部角色 | 私聊及 @ 消息（含 Bot 的 @）、发送/读取/更新消息、表情回复、附件、群信息和 Bot 群成员访问、交互卡片、Bot 基本信息 |
| 管理者额外权限 | 创建/更新任务群、管理群成员、接收未 @ 的群消息（含 Bot 消息） |
| 管理者用户身份权限 | `im:feed_group_v1:read`、`im:feed_group_v1:write`、`offline_access`，用于个人会话标签 |

方案制定者、开发者、测试者、审查者当前操作本地代码和任务，因此使用同一套消息协作基础权限，不会因为角色名字而申请邮箱、日历或全量文档权限。角色权限清单集中在 `cmd/cc-connect/role_permissions.go`，与 Codex/Claude Code/Trae 后端无关。

所有角色都需要应用身份的 `im:chat.members:read`，用于通过自己的应用确认已加入项目群；`im:chat.members:bot_access` 不能替代这个查询权限。已有 Bot 如果缺少它，可在管理者私聊的角色权限入口补齐，无需重建 Bot。管理者仍负责邀请成员，只有入群确认成功后才会登记项目成员。

已经生效的权限会被跳过。飞书 [权限查询](https://open.feishu.cn/document/application-v6/scope/list) 按 `scope_type + scope_name` 区分用户和应用身份。对于已配置但未获批的权限，在所有待批权限均属于当前角色时自动调用 [管理员申请接口](https://open.feishu.cn/document/application-v6/scope/apply)。该接口没有选择 scope 的请求体，不能自动添加未配置的 scope，也不能用它代替个人 OAuth。

未配置的权限会按应用身份、用户身份分别生成预选批量确认链接；用户/管理员点击确认后生效。界面明确区分“已生效”“已提交、待批准”和“暂时无法核验”。申请按应用持久化记录并限制 15 分钟内不重复提交，避免重试或重启反复催审；记录不保存访问令牌。

已存在的 Bot 也可在管理者私聊打开 `/team permissions`（或 `/help → 团队管理 → 角色权限`），选择 Bot 检查并补申请；成员设置卡也提供入口。权限未生效时再次检查同一 Bot 即可，无需重新创建。个人标签授权仍通过管理者私聊的 `/team labels` 完成。

### 后端多目录配置

项目群建议使用上述 Help 表单；不用修改各 Bot 的全局工作目录。Codex、Trae 的静态后端配置也支持 `additional_dirs = ["/absolute/extra"]`，与 `work_dir` 搭配。Codex 将目录传到 exec 配置或 app-server 的 thread/start、thread/resume 配置中；已有审批与沙箱策略保持不变（只读模式仍需审批才能写入）。

Trae ACP 使用已协商的 `sessionCapabilities.additionalDirectories`，在新建、恢复会话时传入 `additionalDirectories`，并非把普通 CLI 的 `--add-dir` 放在 `acp serve` 前。已实测本机 Trae 0.207.1；不声明该能力的旧版本会明确报错。默认识别可执行文件名 `traecli`；自定义包装器须在 ACP options 设置 `project_directory_mode = "trae"`，仍需通过协议能力检查。普通 ACP 服务不会自动套用 Trae 配置。Trae 为附加目录生成自定义权限配置时可能不展示模式选择器，启动时仍会应用已设置的审批模式。

目录按项目隔离；同一项目所有角色使用同一主目录和附加目录列表。它不是多个并列的进程工作目录，也不会自动创建 Git worktree 或解决并发文件修改冲突。


## 任务总览、话题和输出模式

项目群现在以持久化任务编号（T001、T002…）组织工作。管理者派工时创建任务入口卡，写明负责人、派工原因、输入范围、预期交付和前置任务。该任务的执行、审批和结论进入入口卡的话题；这不要求给整个群开启话题隔离。重试必须带原任务编号，复用原话题、过程卡和结论卡；长内容继续使用续卡，不使用翻页按钮。

项目总览原位更新，显示目标、项目是否暂停、最近 12 个任务的负责人和状态，以及失败/阻塞的具体信息。全部任务仍持久化，可通过任务清单查看；超过 12 个时清单以文件提供。历史项目保留成员报告，不根据旧报告猜测或自动重新派工。

- `/project board`：创建或刷新唯一项目总览。
- `/project tasks`：查看完整任务清单。
- `/project task T001`：查看任务说明、状态和交付摘要。
- `/project task T001 logs`：下载工具日志（每条最多 8000 字符、每任务约 2 MiB，不记录模型内部推理）。
- `/project display compact`：默认简洁模式，只显示状态、当前操作与操作数量，审批和结论完整保留。
- `/project display standard`：在摘要中增加最近一条面向用户的进展说明。
- `/project display debug`：显示工具调用与输出，仍不展示内部推理。

显示设置保存在项目中，从后续执行回合生效。命令行只展示紧凑摘要和状态，不提供详情跳转；旧卡片的详情回调仍兼容。管理者收到无需决策的自动回报时静默更新总览，不生成空过程卡。角色自动注册的用途说明继续使用 `--reason`，展示给扫码授权的用户。

管理者工具调用示例：

```sh
cc-connect-team team dispatch --to developer-a --title "实现登录修复" --reason "方案 T001 已验收" --deliverable "补丁、回归测试结果" --depends-on T001 --message "按 docs/login-plan.md 实现并验证"
cc-connect-team team status
cc-connect-team team accept --task-id T002 --evidence "已检查补丁与回归测试结果，满足方案验收标准"
cc-connect-team team dispatch --to developer-a --task-id T002 --reason "修正验收发现的空输入问题" --message "补充空输入处理与用例"
```

Agent 回合结束只会将任务标为「已提交·待验收」，不会自动成为「已验收」。`accept` 要求管理者提供检查依据；只有已验收的依赖才能进入后续派工。失败、中断、停止或待验收任务可带原编号返工；已验收任务的新需求应创建新任务。

## 项目级暂停与恢复

项目群管理员发送 `/project pause` 会持久化暂停状态，停止此项目内所有成员的会话，并清除已进入执行会话的排队输入；尚未派发的管理者待办保留。暂停后禁止新派工、后台调度和自动补建角色；迟到的回报不会唤醒管理者或恢复已停止任务。该状态在服务重启后保留，不影响其他项目。

`/project resume` 由用户在项目群发起，只恢复接收新工作，不自动重派已停止任务。需要继续某个任务时，由管理者带任务编号和具体原因重新派工。单个成员的 `/stop` 仍只停止对应会话；项目级暂停与它是不同范围的操作。`/help` 的项目管理和 `/project settings` 包含这些入口和说明。

本机管理工具也可执行 `cc-connect-team team pause --from <管理者 ID> --session-key <项目会话>`（Unix socket `/team/action` 的 `pause` action）。恢复仅由项目群中的用户执行 `/project resume`，管理者工具不提供自动恢复操作。


## v0.11 项目成员持续会话与管理者待办

同一项目的同一成员（包括管理者）跨任务、返工、结果消息继续同一模型会话。每次群消息仍各有独立的公开过程话题；话题路由不决定模型上下文。不同项目隔离，普通空闲不重置项目会话。显式 `/new` 重置该项目内该成员的会话；历史任务和消息保留。升级已有项目时沿用该成员最近使用的本项目会话，其余旧会话保留，不合并原生模型历史。

项目成员会话在创建或恢复时自动命名为 `项目名 · bot 显示名`，例如 `容器动态挂载 · Johnson`。Codex App Server 和 Trae CLI 的原生会话列表同步使用该名称；其他后端保留 cc-connect 内部名称。显示名来自团队成员的 `display_name`，未设置时沿用该成员的默认标签。命名异步执行且限制等待时间，失败记录日志并在下次恢复时重试，不阻塞任务、不额外创建会话或模型轮次。旧的非当前会话不批量改名，普通私聊不受影响。

管理者通过 `plan` 持久保存后续事项；`planned` 是尚未派发，不发送群消息、不 @ 成员、不占用执行会话。需要时用 `plan --task-id` 修改同一待办，使用 `cancel --task-id` 取消。依赖可以引用未完成的已有任务，循环依赖会拒绝。管理者在结果到达后读取状态，检查并验收产物、更新后续输入，再显式 `dispatch --task-id` 发布就绪任务。

```sh
cc-connect-team team plan --to developer-a --title '补充失败诊断' --deliverable '补丁与测试' --message '在回滚修复上补充诊断' --depends-on T001
cc-connect-team team accept --task-id T001 --evidence '已检查回滚修复及测试'
cc-connect-team team dispatch --task-id T002
cc-connect-team team cancel --task-id T003
```

同一成员只执行一项任务，问答或审批等待仍占用它。忙碌、未验收或依赖版本失效时派工会拒绝，且不先发送任务消息。不同成员可以执行独立任务。结果提交、管理者验收、发布后续任务分别记录；完成、验收、服务重启或恢复项目都不会绕过管理者自动释放所有待办。成员只返回自身执行结果，不维护队列或判断依赖。连续会话中的问题和审批按原话题及请求令牌匹配，旧话题不能回答新请求。


## 结束项目（v0.12）

在项目总览或设置点击“结束项目”，或发送 `/project finish`，核对任务数量和影响后确认。只有具备项目管理权限的用户可以结束；管理者交付最终答复不会自动结项。

结束会停止全体成员，关闭待回答/审批请求，取消未派发待办；保留群聊、历史和产物，未验收结果不会被标成完成。任务状态变化时需要重新确认。`/project resume`、旧回调、旧创建请求都不能重新开启已结束项目；`/project board`、`/project tasks` 和任务详情/日志继续可查。
