## 已接入运行版本

- 用户主指令由管理者在指令话题处理；新任务以群主聊天消息真实 @ 成员，成员执行和原始结果回复到对应任务话题。
- 返工保留同一任务与话题，追加新的执行轮次及卡片，保留先前结果。重复消息去重，排队返工在获得执行权后开始新轮次，旧轮次结果不能覆盖新结果。
- 成员只交付本任务结果。管理者确认前序任务及其执行版本后才能发布依赖任务；前序返工后，基于旧输入的依赖结果不能直接放行。
- 展示公开模型输出、完整工具输入和结果；不展示未公开的内部推理，不生成替代原文的流程摘要。管理者和成员使用相同展示机制。
- 卡片按完整段落／工具调用分组，续卡留在同一话题，不分页切断命令。长命令和输出分别折叠；运行中的调用固定在原卡。单个内容单元超出预算时，完整原文上传为同话题文件。
- Codex app_server 原生问答和权限请求进入群主聊天提醒，真实 @ 原任务发起人；通过引用原任务消息提供来源入口。原选项、文字输入、允许本次和拒绝均绑定原请求。卡片显示实际期限，提交成功更新原卡，回答回原任务。
- 指定用户、群和有效请求校验；旧按钮、重复决定、过期决定不执行。超时和显式停止关闭当前决定，不自动代答或批准。
- Trae ACP 权限审批使用同一提醒链路；启动参数继续保持 `--permission-mode auto acp serve`。auto 只影响权限策略，不代表自动回答需求问题。

## 待验收和能力边界

- 真实飞书桌面端与手机端：提及通知、群主聊天引用提醒、表单点击、任务话题入口、卡片展开和附件访问。当前自动化通过不等于这些客户端体验已验收。
- Trae 当前 ACP 适配尚未接入原生结构化提问；不能把权限审批支持描述为原生问答支持。
- 可选私聊催办默认关闭，本次未实现；不会向用户额外发送私聊。
- 旧请求在重启后不会恢复为可执行审批。异常退出后旧卡外观的主动刷新仍需完善和真实重启验收，不能仅凭旧卡视觉状态判断请求有效。
- 超大审批请求、附件投递失败与后端异常退出仍需专项实测；本次完整附件策略覆盖执行记录，不承诺任意大小的审批卡。
- `/project task logs` 是有容量限制的诊断记录；原始长输出以任务话题中的完整文件为准。
- 不支持由机器人统一隐藏所有用户首页的话题入口，不自动修改个人消息设置。

建议验收顺序：恢复项目 → 发布一项开发任务 → 在原话题 @ 成员返工 → 触发一条问答及一条需决定的权限请求 → 验证原卡更新、原任务继续和前序确认前无后续派工。
