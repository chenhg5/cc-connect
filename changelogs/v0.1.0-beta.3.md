# cc-connect-next v0.1.0-beta.3

## 中文

这一版只做一件事：让第一次安装在出错时说人话。上一版的走查发现，配置没改完照样能「启动成功」，而真正的体检工具只存在于聊天里——恰恰是连不上时用不到的地方。

### 变化

- **占位配置不再假装启动成功。** 首次运行生成的配置里，`work_dir`、`app_id`、`app_secret` 都是标了 `REPLACE` 的占位值。只要还有一个没替换，启动就在创建任何引擎之前拒绝执行，逐条列出「哪个项目、哪个键、下一步做什么」。此前它会先打印 `platform ready`、`engine started`、`cc-connect-next is running`，再被飞书以 `app_id is invalid` 拒绝，然后静默挂起。
- **`cc-connect-next doctor` 成为真正的命令。** 原先只有 `doctor user-isolation` 一个子命令，`--help` 里也没有它。现在不带子命令即运行完整体检：配置文件与占位值、工作目录、Agent 命令行与登录态、每个平台的配置校验、本地依赖、网络连通性；任一项失败退出码为 1。全过程不建立任何平台连接（因此平台一项不会谎称 `connected`），实例没跑起来时同样可用。`--config` / `--project` 可缩小范围，`doctor user-isolation` 行为不变，Windows 上完整体检现在也能用。
- **凭据对了但连不上时,启动不再沉默。** 长连接是在 Start 返回之后才建立的,所以「running」永远早于第一次连接结果。现在启动 30 秒后会复查一次,把仍然不可用的平台连同原因写成一条 ERROR 日志,并指向 `doctor`。
- **首次运行的模板与推荐飞书配置合并为一份定义。** 模板不再自带一套写法（全局 `[display]`、固定的 `normalize_agents`、缺三项平台设置），而是由 `config.RecommendedFeishuProfile` 渲染，与 `feishu setup` 套用的完全一致，并有测试锁定二者不得漂移。
- **推荐配置补回 `hide_agent_footer = true`。** 配置示例、飞书文档与卡片契约一直这么写，只有 PR #17 固化的预设漏了它。

### 影响

- 新装用户拿到的配置改为项目级 `[projects.display]`、不再固定 `mode`，并显式包含 `enable_feishu_card`、`thread_isolation`、`group_reply_all`。`group_reply_all = true` 表示群里不需要 @ 也会回答，模板在该键下方直接给出 `allow_from` / `allow_chat` 的作用域示例。
- 已有配置行为不变：拒绝只针对本工具自己写下的占位值，用户自己填的任何值都不会被二次猜测。
- 配置里的 `work_dir` 不存在时，启动记一条警告（挂载未就绪是合法场景），`doctor` 判为失败。

### 升级

```bash
npm install -g cc-connect-next@beta
```

`v0.1.0-beta.1` / `beta.2` 可直接升级。官方 CC Connect 的二进制、配置目录、daemon 和飞书连接不受影响。

## English

This release does one thing: make a first install explain itself when it goes wrong. The previous walkthrough found that a half-edited config still "started successfully", and that the real health check existed only inside chat — exactly where you cannot reach it when nothing connects.

### Changes

- **A placeholder config no longer pretends to start.** The generated first-run config marks `work_dir`, `app_id` and `app_secret` as `REPLACE`. While any of them is unreplaced, startup refuses before building a single engine and lists project, key, and the step that resolves it. Previously it printed `platform ready`, `engine started` and `cc-connect-next is running`, was then rejected by Feishu with `app_id is invalid`, and hung there looking healthy.
- **`cc-connect-next doctor` is a real command.** It used to expose only the `user-isolation` subcommand and was absent from `--help`. With no subcommand it now runs the full check: config file and placeholders, work directory, Agent CLI and login state, per-platform configuration validation, local dependencies, and network reachability, exiting 1 if any check fails. It opens no platform connection — so the platform section never claims `connected` — and therefore works while the instance is down. `--config` and `--project` narrow it; `doctor user-isolation` is unchanged; the full check now also runs on Windows.
- **A working credential that still cannot connect is no longer silent.** The long connection is established after Start returns, so "running" always precedes the first connection result. Startup now checks back after 30 seconds and logs the platforms that are still unusable, with the reason, pointing at `doctor`.
- **The first-run template and the recommended Feishu profile are one definition.** The template no longer carries its own spelling (a global `[display]`, a fixed `normalize_agents`, three missing platform settings); it is rendered from `config.RecommendedFeishuProfile`, the same definition `feishu setup` applies, with a test that keeps them from drifting.
- **The recommended profile regains `hide_agent_footer = true`**, which the example config, the Feishu guide, and the card contract have always documented.

### Impact

- New installations get project-level `[projects.display]`, no pinned `mode`, and explicit `enable_feishu_card`, `thread_isolation`, and `group_reply_all`. `group_reply_all = true` answers group messages without an @mention, so the template puts the `allow_from` / `allow_chat` scope right below that key.
- Existing configurations behave exactly as before: the refusal only recognises placeholder values this tool wrote itself and never second-guesses a value you chose.
- A configured `work_dir` that does not exist is a startup warning (a mount that is not up yet is a real deployment) and a `doctor` failure.

### Upgrade

```bash
npm install -g cc-connect-next@beta
```

`v0.1.0-beta.1` and `beta.2` upgrade in place. The official CC Connect binary, data directory, daemon, and Feishu connection are unaffected.
